# 家計簿アプリ 要件定義書

## 第6章 技術スタック書（一次開発）

[MVP範囲書](02_MVP範囲書.md)・[機能一覧書](05_機能一覧書.md)で定義した機能を実現するための技術構成と、その選定理由・想定されるデメリットを整理する。
個人開発（一人でのフル実装・運用）を前提とし、**学習コストと開発スピードのバランス** を重視した選定とする。

---

### 1. 技術スタック一覧

| レイヤー | 採用技術 | 主な選定理由（要約） |
|---|---|---|
| 言語 | TypeScript | フロントエンド・バックエンド共通で型を付け、実行前にバグを検出できる |
| バックエンド | Node.js | フロントエンドと言語を統一でき、必要な部品（認証・ORM等）がnpmエコシステムに揃っている |
| フロントエンド | React.js | コンポーネント指向で画面間の再利用がしやすく、状態管理・UIキット・チャートライブラリが揃っている |
| DB | PostgreSQL | リレーショナル設計による正規化がしやすく、JSON型による柔軟性、DB側での集計処理も可能 |
| 開発環境 | Docker | PostgreSQLを含むローカル開発環境をコマンド1つで再現できる |
| ホスティング（フロントエンド） | Vercel | 無料枠でReactアプリを公開でき、GitHubへのpushだけで自動デプロイされる |
| ソース・文書・タスク管理 | GitHub（Issue含む） | ソースコード・本要件定義書を含むドキュメント・タスク（Issue）を一元管理する |

---

### 2. 選定理由の詳細（要件との紐付け）

#### 2-1. バックエンド：Node.js

| 選定理由 | 要件定義との紐付け |
|---|---|
| フロントエンドもJavaScript（React）で統一できるため、言語切り替えのコストが発生しない | 個人開発で1人が全レイヤーを実装する構成のため、言語を分けた場合に発生する文脈切り替えコストをなくし、[MVP範囲書](02_MVP範囲書.md)の4機能（FUC-001〜013）を最短で実装することに直結する |
| npmエコシステムが巨大で、認証（Passport / Auth.js）やORM（Prisma等）など必要な部品が揃っている | 現時点のMVPは[ユーザ登録・ログイン機能を対象外](02_MVP範囲書.md#3-mvpで対象外とする機能)としているが、将来的に複数端末・複数ユーザー対応を検討する際に認証基盤をゼロから自作せずに済む。またORM（Prisma）は、[機能一覧書](05_機能一覧書.md)にある収支・固定費・カテゴリ・カテゴリ区分の4テーブル程度のリレーション管理・マイグレーションを型安全に行えるため、FUC-001〜FUC-010・FUC-014〜FUC-017（登録・編集・削除系機能）の実装・保守コストを下げる |

#### 2-2. フロントエンド：React.js

| 選定理由 | 要件定義との紐付け |
|---|---|
| コンポーネント指向のため、UIを再利用しやすい | [画面一覧書](03_画面一覧書.md)のSCR-002（収支入力）とSCR-004（固定費登録）、SCR-003（収支一覧）とSCR-005（固定費一覧）は入力・一覧という構造が共通しており、入力フォームやテーブルコンポーネントを共通化することで開発工数を削減できる |
| 状態管理（Zustand等）・UIキット（shadcn/ui等）・チャートライブラリ（Recharts等）が揃っており、一から作る必要がない | 特にチャートライブラリは、FUC-011（月次収支グラフ）・FUC-012（カテゴリ別支出グラフ）・FUC-013（削減対象カテゴリ内訳表示）というMVPの中核機能（[目的1：支出・収入の見える化](01_目的と背景.md#1-目的)）に直結する。グラフ描画を自作しないことで、可視化という本質的な価値提供に開発リソースを割ける |

#### 2-3. DB：PostgreSQL

| 選定理由 | 要件定義との紐付け |
|---|---|
| 4テーブル程度を作成し、リレーションを組む必要があるため、正規化がしやすい | 収支データ・固定費データ・カテゴリマスタ・カテゴリ区分（削減対象／維持対象）という関連し合うデータ構造（[機能一覧書](05_機能一覧書.md)FUC-001〜FUC-010）を、整合性を保ちながら管理できる |
| JSON型もサポートしているため、柔軟なデータを登録できる | 収支のメモ欄や、将来カテゴリごとに項目を拡張したい場合など、スキーマを固定しきれない付随情報を無理にテーブル分割せず柔軟に保持できる |
| 集計をバックエンド・フロントエンドで構築する必要がない | FUC-009（固定費自動計上）による月次反映や、FUC-011〜013のグラフ表示に必要な「月次合計」「カテゴリ別合計」「削減対象カテゴリ合計」を、SQLの集計関数（GROUP BY等）でDB側に任せられる。これによりアプリケーション側で重複した集計ロジックを持たずに済み、[背景2-2](01_目的と背景.md#2-2-削ってよいものの基準がないまま節約しようとする辛さ)で定義した「削減対象の可視化」の正確性・保守性が高まる |

#### 2-4. GitHub（Issueによるタスク管理を含む）

| 選定理由 | 要件定義との紐付け |
|---|---|
| ソースコード・文書を一元管理する | 本要件定義書（目的と背景／MVP範囲書／画面一覧書／機能一覧書等）とソースコードを同一リポジトリまたは関連リポジトリで管理することで、機能追加時に「なぜこの機能があるのか」を常にドキュメントへ遡って確認できる状態を保つ |
| タスク管理にGitHubのIssueを使用する | タスクをコードと同じ場所で管理することで、コミット・プルリクエストとIssueを紐づけられる（例：コミットメッセージやPR本文に `#12` と書く、`Closes #12` でマージ時にIssueを自動クローズする）。「どのタスクのためにどのコードを変更したか」を追跡でき、タスクとコードの管理を一元化できる。機能一覧書のFUC単位でIssueを作成すれば、要件・タスク・コードを対応づけられる |

#### 2-5. 言語：TypeScript

| 導入目的 | 要件定義との紐付け |
|---|---|
| JavaScriptに静的型を付け、実行前（コンパイル時）にバグを検出する | レビュアー不在・テストも開発者自身が行うという[リソース制約](00_システム全体概要書.md#13-制約)のもとでは、人の目によるチェックに頼れない。型チェックを「もう一人のレビュアー」として機能させ、実行時まで気付きにくい不具合（[3. デメリット](#3-今後の開発で想定されるデメリット注意点)のNode.jsの項）を減らす |
| Prismaと組み合わせ、DBスキーマとコードの型を連動させる | 収支・固定費・カテゴリ・カテゴリ区分のテーブル定義が変わった際、影響を受けるコードがコンパイルエラーとして洗い出されるため、FUC-001〜FUC-010・FUC-014〜FUC-017（登録・編集・削除系機能）の修正漏れを防げる |
| フロントエンドとバックエンドで型定義を共有する | API仕様書で定義したリクエスト・レスポンスの型を両側で共有することで、画面（SCR-001〜009）とAPIの間の項目名・型の不一致を防ぐ |

#### 2-6. 開発環境：Docker

| 導入目的 | 要件定義との紐付け |
|---|---|
| PostgreSQLのローカル開発環境をコンテナで構築する | [3. デメリット](#3-今後の開発で想定されるデメリット注意点)のPostgreSQLの項で挙げた「ローカル開発環境構築を自前で担う負荷」を軽減する。PCに直接DBをインストールせずに済み、環境の作り直し・初期化も容易になる |
| 開発環境の構成をコード（Dockerfile・docker-compose.yml）として残す | 個人開発では環境構築の手順が記憶頼みになりやすい。構成ファイルをGitHubで管理することで、PCの買い替えや時間を空けた再開時にも同じ環境を再現できる |
| Node.js・PostgreSQLのバージョンを固定する | ローカルと本番（Render・Supabase等）でバージョンをそろえることで、「ローカルでは動くが本番で動かない」という差異を減らす |

#### 2-7. ホスティング（フロントエンド）：Vercel

| 導入目的 | 要件定義との紐付け |
|---|---|
| 無料枠（Hobbyプラン）でフロントエンドを公開する | サーバーは無料〜低コストのホスティングに収めるという[技術的制約](00_システム全体概要書.md#13-制約)を満たす |
| GitHubと連携し、pushするだけで自動デプロイする | 開発者1名の体制では、デプロイ作業を毎回手作業で行う手間・ミスを減らす必要がある。ビルドからデプロイまでを自動化し、開発に時間を割ける |
| プルリクエストごとにプレビュー環境が自動で作られる | 本番に反映する前に、対応ブラウザ（Chrome・Edge・Firefox）やスマートフォンで表示を確認できる。スマホブラウザ優先・表示崩れ防止という[環境制約](00_システム全体概要書.md#13-制約)の確認に役立つ |

### 3. 今後の開発で想定されるデメリット・注意点

技術選定はMVPの実現速度を優先したものであり、開発が進むにつれて以下の点が課題になる可能性がある。

| 技術 | 想定されるデメリット | 備考・対策の方向性 |
|---|---|---|
| Node.js | シングルスレッドのため、グラフ集計等CPU負荷の高い処理を大量に・同時に実行すると応答性能が低下する可能性がある | 個人利用（単一ユーザー）が前提のMVPでは影響は小さいが、将来複数ユーザー対応する場合は集計処理の非同期化・キャッシュ設計が必要になる |
| Node.js | JavaScriptのみで実装すると型がなく、実行時までバグに気付きにくい（特にDBスキーマとコードの不整合） | TypeScriptを導入する（[2-5](#2-5-言語typescript)参照）。Prismaと組み合わせることでDBスキーマとコードの型を連動させ、リスクを軽減する |
| React | エコシステムの変化が早く、UIキットや状態管理ライブラリのメジャーバージョンアップ・非推奨化に追随するメンテナンスコストが発生する | 個人開発では追随の判断を後回しにしやすく、放置すると依存パッケージが古いまま脆弱性を抱えるリスクがある。定期的な依存関係の棚卸しが必要 |
| React | コンポーネント設計を誤ると、画面（SCR-001〜009）間で似て非なるコンポーネントが乱立し、かえって再利用性のメリットを活かせなくなる | 入力フォーム・一覧テーブル・グラフ表示など、機能一覧書のFUC単位で共通コンポーネントを最初に設計しておく必要がある |
| PostgreSQL | リレーショナルDBはスキーマ変更（カラム追加・テーブル分割等）にマイグレーション作業が伴い、変更コストがNoSQLより高い | カテゴリ区分の粒度など、要件が固まりきっていない部分は先にJSON型で柔軟に持たせ、要件確定後に正規化するといった段階的な設計も検討できる |
| PostgreSQL | 個人開発の場合、DBサーバーの運用（バックアップ・冗長化・ローカル開発環境構築）を自前で担う必要がある | ローカルはDockerでコンテナ化し（[2-6](#2-6-開発環境docker)参照）、本番運用はマネージドサービス（Supabase、Neon等のPostgreSQL互換サービス）の利用を検討し、運用負荷を下げる方向が望ましい |
| TypeScript | 型定義の記述やコンパイル設定（tsconfig）の分だけ記述量・学習コストが増え、型エラーの解消に時間を取られる場面がある | `any` の多用で型の恩恵を失わないよう注意しつつ、最初から厳密にしすぎず段階的に型を強化する |
| Docker | Docker自体の学習コストがあり、Windows環境ではDocker Desktop・WSL2の導入やメモリ消費が負担になる | MVPではDBのみをコンテナ化するなど、利用範囲を絞って始める |
| Vercel | Hobbyプランは非商用の個人利用に限られ、転送量・ビルド時間などに無料枠の上限がある。またフロントエンド（Vercel）とバックエンド（Render等）が別サービスになるため、CORSや環境変数（APIのURL等）を両方で管理する必要がある | 個人利用のMVPでは無料枠内に収まる想定。将来、商用化する場合は有料プランへの移行を検討する |
| GitHub Issue | 外部のタスク管理ツール（Notion、Trello等）に比べ、ガントチャートや詳細な進捗管理の機能が少ない。Issueの粒度や書き方に決まりがないと、タスクが増えたときに把握しづらくなる | 個人開発のMVP規模であれば、ラベル・マイルストーン・GitHub Projects（かんばん）で足りる想定。Issueの粒度（FUC単位など）とラベルの運用ルールをREADMEに記載する |
| GitHub | 個人開発ではプルリクエストレビューのような複数人開発のメリットを活かせず、Actions（CI/CD）の実行時間・Privateリポジトリの容量に無料枠の上限がある | MVPの規模であれば無料枠内に収まる想定だが、CI/CDを充実させるほど実行時間を消費する点は留意する |

### 4. まとめ

本技術スタックは、「[目的と背景](01_目的と背景.md)」で定義した **入力負担の解消** と **支出の見える化** を、個人開発でも最短で実現することを最優先に選定した。特にグラフライブラリ・ORM・DBの集計機能など「一から作らずに済む」部品を積極的に活用することで、開発リソースをコア機能（固定費の自動計上、削減基準に基づく可視化）に集中させる構成となっている。

一方で、個人開発ゆえの運用・保守面の負荷（依存関係の追随、DB運用、マイグレーション管理）は今後の課題として認識し、機能拡張のタイミングで都度見直しを行う。
