### 5. 固定費（fixed_expenditures）

支出（expenditures）テーブルとは別テーブルとしている。固定費は「毎月／毎年、支出として自動計上される元データ（テンプレート）」であり（[機能一覧書](05_機能一覧書.md)のFUC-009 固定費自動計上機能）、ユーザーが都度入力する実際の支出取引そのものではないため。同一テーブルに持たせると、頻度・自動計上フラグなど固定費にしか使わない列が、通常の支出行では常にNULLになってしまう。

| 論理名 | 物理名 | 型 | NOT NULL | UNIQUE | 補足 |
|---|---|---|---|---|---|
| 固定費Id | fixed_expenditure_id | INTEGER | 〇 | 〇 | PK。`GENERATED BY DEFAULT AS IDENTITY`による自動採番 |
| 支出カテゴリー | expenditure_category | INTEGER | 〇 |  | FK。categoriesテーブルのcategory_idと紐づける |
| 固定費金額 | fixed_amount | NUMERIC(6,0) | 〇 |  | 金額型。1〜999999の範囲のみ許可（CHECK制約で0以下を禁止） |
| 固定費名称 | fixed_name | VARCHAR(30) | 〇 |  | 一覧で識別するための名称（例：「家賃」「動画サブスク」）。30桁まで。重複可（UNIQUE制約なし） |
| 計上頻度 | fixed_frequency | CHAR(2) | 〇 |  | 「01」または「02」のみ許可（CHECK制約で制限）。01は毎月、02は毎年 |
| 開始日 | fixed_start_date | DATE | 〇 |  | 自動計上を開始する日付。画面（SCR-004）のカレンダーで選択した日付をそのまま保持する（例：2026-10-15）。月初日への変換はしない。**計上日はこの日付から決める**（毎月：dd／毎年：MM/dd）。該当月にその日が存在しない場合（例：2月31日）は月末日に計上する |
| 固定費ユーザ | fixed_user | INTEGER | 〇 |  | FK。usersテーブルのuser_idと紐づける。固定費の持ち主。自動計上（FUC-009）で支出を作成する際、expendituresのexpenditure_userにこの値を設定する |
| 次回計上日 | fixed_next_posting_date | DATE | 〇 |  | 次に自動計上（FUC-009）する日付。登録時・開始日や計上頻度の変更時に計算する（開始日が明日以降なら開始日、今日以前なら今日の翌月以降で最初に来る計上日）。計上後は次の計上日へ更新する。計上済みかどうかの判定にも使う |
| メモ | fixed_memo | VARCHAR(200) |  |  | 任意（NULL可）。200桁まで |
| 論理削除フラグ | is_delete | BOOLEAN | 〇 |  | true:論理削除済み／false:有効。デフォルトfalse |

### 6. カテゴリー区分（category_classification）

usersテーブルとcategoriesテーブルの中間テーブル。1人のユーザーが、どのカテゴリーを「削減対象」とするかを、優先度・削減金額と合わせて紐づけるためのテーブル。

削減金額はカテゴリー単位で持つ。固定費（fixed_expenditures）と変動費（expenditures）はどちらも支出用カテゴリーに紐づくため、1つのカテゴリーの削減金額で固定費・変動費の両方をまとめて扱う。

| 論理名 | 物理名 | 型 | NOT NULL | UNIQUE | 補足 |
|---|---|---|---|---|---|
| カテゴリー区分Id | category_classification_id | INTEGER | 〇 | 〇 | PK。`GENERATED BY DEFAULT AS IDENTITY`による自動採番 |
| 削減対象カテゴリー | reduction_category | INTEGER | 〇 |  | FK。categoriesテーブルのcategory_idと紐づける |
| 削減優先対象 | reduction_number | SMALLINT | 〇 |  | 削減優先度。1〜3（1が最優先）。同一ユーザ内で重複・欠番なし。削減対象は1ユーザあたり最大3件 |
| 削減金額 | reduction_amount | NUMERIC(6,0) | 〇 |  | 1か月あたりに削減してよい金額。金額型。1〜999999の範囲のみ許可（CHECK制約で0以下を禁止） |
| 削減対象ユーザ | reduction_target_user | INTEGER | 〇 |  | FK。usersテーブルのuser_idと紐づける |
| 論理削除フラグ | is_delete | BOOLEAN | 〇 |  | true:論理削除済み／false:有効。デフォルトfalse |

### 7. 今後の検討事項

- 各テーブルのPKカラムは`SERIAL`ではなく`INTEGER GENERATED BY DEFAULT AS IDENTITY`を採用する。アプリケーション側から明示的に値を指定した採番（データ移行時など）も許容しつつ、通常はDBが自動採番するSQL標準準拠の書き方のため。
- `gender` は将来的に選択肢が増える可能性があるため、CHECK制約ではなくマスタテーブル化する余地がある。
- `category_type`によるカテゴリの支出用／収入用の判定は、アプリケーション側またはDBの制約（CHECK制約やトリガー）で、expenditure_category/income_categoryとの整合性を保証する必要がある。
- FUC-009（自動計上）で計上済みかどうかの判定は、次回計上日（fixed_next_posting_date）で行う。
- fixed_expendituresから自動生成されたexpendituresのレコードを識別するため、expenditures側に元の固定費を参照するFK（例: source_fixed_expenditure_id）の追加を検討する。
- category_classificationは現状「削減対象」の紐づけのみを表現しており、「維持対象」は非登録として扱う想定。区分を明示的に持たせたい場合はカラム追加を検討する。
- カテゴリーの編集・削除はSCR-006で行う。一次開発では以下の方針とする（詳細は[SCR-006詳細設計](20_詳細設計書_SCR-006カテゴリ設定.md)）。
  - 編集・削除できるのは、自分が作成したカテゴリー（`category_creater_user`=自分、かつ`default_category`=false）のみ。デフォルトカテゴリーは編集・削除できない。これにより、1人の削除操作が他ユーザーのデータに波及しない。
  - カテゴリーを削除（論理削除）したときは、同じトランザクションで自分のcategory_classificationの該当レコードも論理削除する。削除したカテゴリが削減対象だった場合は、同じトランザクションで残りの削減対象の`reduction_number`を、1から欠番のない連番に自動で詰め直す（例：1・2・3のうち2番目を削除 → 1番目は変更なし、3番目が2番目になる）。`reduction_amount`は変更しない。
  - 有効な固定費（fixed_expenditures.is_delete=false）が使用しているカテゴリーは削除できない（削除すると、以降の自動計上で削除済みカテゴリーの支出が作られてしまうため）。
  - expenditures／incomesは履歴として残し、連動削除しない。
  - `category_name`はテーブル全体でUNIQUEのため、他ユーザーが作成したカテゴリーと同名は登録できない。複数ユーザー対応時は「作成者＋カテゴリー名」での一意制約への変更を検討する。
- 以下は二次開発（複数ユーザー対応）時に改めて方針を決める。
  - categoriesは`default_category`により複数ユーザーで共有されうるため、1人のユーザーの削除操作でカテゴリー自体（categories.is_delete）を論理削除すると、同じカテゴリーを使う他ユーザーのcategory_classificationまで一括で連動削除されてしまう。「自分がこのカテゴリーの利用をやめる（自分のcategory_classificationのみ削除）」と「カテゴリー自体を廃止する」は区別して扱う必要がある。
  - category_creater_user以外のユーザーが、default_category=trueの共有カテゴリーを削除できるかどうか（削除権限の範囲）を決める必要がある。
  - カテゴリーを復元(is_delete=false)した際、連動削除したcategory_classificationも自動復元するかどうかを決める必要がある（自動復元すると、ユーザーが個別に外していた設定まで復元されてしまう可能性がある）。
  - expenditure_category/income_categoryには同様の連動削除を行わない想定（支出・収入は履歴として残すため）。category_classificationとの扱いの違いを設計意図として明記しておく。
- `is_delete`のDEFAULT falseはINSERT時に値を省略した場合にのみ適用され、UPDATE文には影響しない。既存レコードを更新する処理（他カラムの編集等）でis_delete列に触れなければ値は保持される。ただし、ORM等で全カラムを一括UPDATEする実装の場合、意図せずis_deleteを上書きしてしまう可能性があるため、削除／復元専用の処理（is_delete列のみを更新する）を通常の更新処理とは分離することを推奨する。
