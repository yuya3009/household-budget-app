# 家計簿アプリ 要件定義書

## 第11章 デプロイ・インフラ方針書（一次開発）

[システム全体概要書](00_システム全体概要書.md)の制約（無料〜低コストのホスティングに収める）と、[技術スタック書](06_技術スタック書.md)で採用した技術（Node.js / React / PostgreSQL / GitHub）を前提に、デプロイとインフラの構成を定める。
個人開発のため、**費用を0円に抑えること** と **GitHubへのpushだけで自動デプロイされること** を重視する。

---

### 1. 採用方針

以下の構成（A案）を採用する。

| 役割 | 採用サービス | 料金 | 自動デプロイ |
|---|---|---|---|
| ソース管理・CI | GitHub / GitHub Actions | 無料 | — |
| フロントエンド（React） | Vercel | 無料（Hobbyプラン） | ◯ GitHubへのpushで自動 |
| バックエンド（Node.js） | Render（Web Service・Docker） | 無料（Freeプラン） | ◯ GitHubへのpushで自動 |
| DB（PostgreSQL・本番） | Neon | 無料（Freeプラン） | — |
| DB（PostgreSQL・開発） | Docker（ローカル） | 無料 | — |

---

### 2. 構成図

```
[開発PC] Docker Compose
  ├ frontend（React）
  ├ backend（Node.js）
  └ db（PostgreSQL）… 開発用DB
        │
        │ git push
        ▼
[GitHub] ──── push を検知して自動デプロイ ────┐
        │                                    │
        ▼                                    ▼
[Vercel] フロントエンド配信        [Render] バックエンド（Dockerfileで起動）
                                             │
                                             ▼
                                     [Neon] PostgreSQL … 本番用DB
```

---

### 3. 選定理由

| サービス | 選定理由 |
|---|---|
| Vercel | Reactのビルド成果物（静的ファイル）を無料で配信でき、GitHub連携だけで自動デプロイ・HTTPS化まで完了する。スマートフォンからの利用（[システム全体概要書](00_システム全体概要書.md) 11章）にも十分な配信速度がある |
| Render | Dockerfileからバックエンドを起動できるため、ローカル開発と同じ環境で本番を動かせる。GitHub連携による自動デプロイが標準で備わっている |
| Neon | PostgreSQLのマネージドサービスで、無料プランに期限がない。バックアップ・バージョン更新などDB運用をサービス側に任せられる（[技術スタック書](06_技術スタック書.md) 3章のPostgreSQLのデメリットへの対策） |
| Docker | 開発用のPostgreSQLをPCに直接インストールせずに済み、`docker compose up` だけで開発環境を再現できる |

---

### 4. 環境の分離

開発用と本番用でDBを分け、接続先は環境変数 `DATABASE_URL` で切り替える。

| 環境 | DB | 接続先の設定場所 |
|---|---|---|
| 開発 | ローカルのDockerコンテナ（PostgreSQL） | リポジトリ直下の `.env`（Git管理外） |
| 本番 | Neon | Renderの管理画面「Environment」に登録 |

- `.env` は `.gitignore` に追加し、GitHubにはコミットしない。
- 必要な変数名の一覧は `.env.example`（値は空またはダミー）としてコミットし、ドキュメント代わりとする。
- 本番DBの接続情報（パスワードを含む）はPCのファイルに保存せず、Renderの環境変数にのみ登録する。
- 本番DBへのマイグレーションは、Renderのデプロイ時に `prisma migrate deploy` を実行して反映する。開発時は `prisma migrate dev` を使用する。

---

### 5. デプロイの流れ

1. ローカル（Docker Compose）で開発・動作確認を行う。
2. GitHubの `main` ブランチへpushする。
3. GitHub Actionsでテスト・Lintを実行する（導入は後から行ってもよい）。
4. Vercelがフロントエンドを、Renderがバックエンドをそれぞれ自動でビルド・公開する。
5. Renderのデプロイ時にマイグレーションが実行され、Neonのスキーマが更新される。

---

### 6. 想定されるデメリット・注意点

| 対象 | 想定されるデメリット | 対策の方向性 |
|---|---|---|
| Render | 無料プランは15分アクセスがないとスリープし、次回アクセス時の起動に30秒〜1分程度かかる | 個人利用では許容する。気になる場合はRenderのみ有料プラン（月7ドル程度）へ変更する |
| Render | 無料プランのPostgreSQLは一定期間で期限切れになる | DBはRenderではなくNeonを利用する |
| Neon | 一定時間アクセスがないとDBが停止し、再開時に若干の待ち時間が発生する | 個人利用では影響は小さい。Renderのスリープ解除と重なる点に留意する |
| Neon | 無料プランは容量（0.5GB/プロジェクト）・計算時間に上限がある | 家計簿のデータ量であれば上限に達しない想定。定期的に管理画面で使用量を確認する |
| 共通 | 無料枠の条件は予告なく変更されることがある | 構築時および定期的に各公式サイトで最新の条件を確認する |
| 共通 | 公開URLとなるため、認証がないと第三者がデータを閲覧できる | 本番公開時は最低限の認証を導入する |
| 共通 | Render・Neonのリージョンが離れていると、API応答が遅くなる | 両者を同じリージョン（例：シンガポール）に揃える |

---

### 7. 将来の見直し方針

- Renderのスリープが運用上の問題になった場合は、Renderの有料プラン、またはRailway（月5ドル〜）への移行を検討する。
- バックエンドをDockerで動かしているため、Google Cloud Run等の他サービスへも大きな改修なしで移行できる。
- データ量・利用者の増加により無料構成で対応できなくなった場合は、「8. 【参考】AWSで構築する場合の案」に沿ってAWSへの移行を検討する。

---

### 8. 【参考】AWSで構築する場合の案

> **本章は参考情報である。一次開発ではAWSで構築しない。**
> 記載の目的は以下の2点とする。
> - AWSの構成・用語への理解を深めるため
> - データ量の増加等により1章の構成で対応できなくなり、AWSへ移行することになった場合に、本章の方針に沿って構築できるようにし、移行作業を円滑にするため
>
> AWSの料金・サービス内容は変更されることがあるため、実際に構築する際は公式情報で最新の内容を確認し、本章を更新したうえで着手する。

#### 8-1. 移行を検討するタイミング（目安）

| 状況 | 内容 |
|---|---|
| DB容量の不足 | Neonの無料プランの容量上限（0.5GB）に近づいた |
| 応答速度の問題 | Renderのスリープ解除待ちが利用上の問題になり、有料プランでも解決しない |
| 利用者の増加 | 複数ユーザー対応などで、可用性・性能・監視の要件が高まった |

#### 8-2. 構成方針

| 役割 | 現行（A案） | AWSでの構成案 | 補足 |
|---|---|---|---|
| フロントエンド配信 | Vercel | Amazon S3 + Amazon CloudFront | ビルドした静的ファイルをS3に置き、CloudFront（CDN）から配信する。HTTPS証明書はAWS Certificate Manager（ACM）で無料発行する |
| バックエンド | Render（Docker） | Amazon ECS on AWS Fargate + Application Load Balancer（ALB） | 既存のDockerfileをそのまま利用できる。Fargateを使うことでサーバー（EC2）の管理が不要になる |
| コンテナイメージ置き場 | （Renderが内部で管理） | Amazon ECR | GitHub Actionsでビルドしたイメージを保存する |
| DB | Neon | Amazon RDS for PostgreSQL | PostgreSQLのままのため、Prismaのスキーマ・コードは変更不要 |
| 環境変数・秘密情報 | Renderの環境変数 | AWS Systems Manager Parameter Store（または AWS Secrets Manager） | `DATABASE_URL` 等をここに保存し、ECSのタスク定義から参照する |
| 自動デプロイ | Vercel・Renderの標準機能 | GitHub Actions | 8-4を参照 |
| ログ・監視 | 各サービスの管理画面 | Amazon CloudWatch（Logs / Alarms） | コンテナのログ出力とエラー検知を行う |
| ネットワーク | （意識不要） | Amazon VPC | 8-3を参照 |
| リージョン | シンガポール | 東京（ap-northeast-1） | 利用者が日本国内のため、全サービスを東京に揃える |

#### 8-3. ネットワーク構成

```
[利用者のスマートフォン]
      │
      ├──▶ [CloudFront] ──▶ [S3] フロントエンド（静的ファイル）
      │
      └──▶ [ALB] ─────────▶ [ECS Fargate] バックエンド
                                   │
┌─ VPC ─────────────────────────────┼──────────────┐
│ パブリックサブネット : ALB, ECS     │              │
│ プライベートサブネット : RDS ◀──────┘              │
└───────────────────────────────────────────────────┘
```

- **VPC**：AWS上に作る自分専用のネットワーク。
- **パブリックサブネット**：インターネットから到達できる区画。ALBを置く。
- **プライベートサブネット**：インターネットから直接到達できない区画。DB（RDS）を置き、外部から直接アクセスされないようにする。
- **セキュリティグループ**：通信を許可する相手を決めるファイアウォール。RDSはECSからの接続（5432番ポート）のみ許可する。
- ECSは費用を抑えるためパブリックサブネットに配置し、セキュリティグループでALBからの通信のみ許可する。プライベートサブネットに置く場合はNATゲートウェイ（月数十ドル）が必要になるため、費用と安全性を比較して判断する。

#### 8-4. デプロイの流れ（GitHub Actions）

1. `main` ブランチへpushする。
2. GitHub Actionsでテスト・Lintを実行する。
3. **バックエンド**：Dockerイメージをビルドし、ECRへpushした後、ECSサービスを更新して新しいコンテナに入れ替える。
4. **マイグレーション**：ECSの単発タスクとして `prisma migrate deploy` を実行する。
5. **フロントエンド**：Reactをビルドし、成果物をS3へアップロードした後、CloudFrontのキャッシュを削除する。

- GitHub ActionsからAWSへの認証は、アクセスキーを保存せず **OIDC（IAMロールの引き受け）** を利用する。アクセスキーの漏えいリスクをなくすためである。

#### 8-5. 移行手順の概要

1. VPC・RDS・ECR・ECS・ALB・S3・CloudFrontを作成する。
2. Neonのデータを `pg_dump` で出力し、`pg_restore` でRDSへ取り込む。
3. Parameter Storeに本番用の `DATABASE_URL`（RDSの接続先）を登録する。
4. GitHub Actionsのワークフローを追加し、AWSへのデプロイを確認する。
5. 動作確認後、フロントエンドのAPI接続先をALB（またはそのドメイン）に切り替える。
6. 一定期間並行稼働させて問題がないことを確認し、Vercel・Render・Neonを停止する。

#### 8-6. 費用の目安（最小構成・東京リージョン・月額）

| サービス | 構成 | 目安 |
|---|---|---|
| ALB | 1台 | 約20ドル |
| ECS Fargate | 0.25vCPU / 0.5GBメモリ × 1タスク | 約10ドル |
| RDS for PostgreSQL | db.t4g.micro・シングルAZ・ストレージ20GB | 約20ドル |
| パブリックIPv4アドレス | 1個あたり | 約3.6ドル |
| S3・CloudFront・ECR・CloudWatch | 小規模利用 | 数ドル程度 |
| **合計** | | **約50〜60ドル** |

- 金額は概算であり、実際の料金は公式の料金ページ・AWS Pricing Calculatorで確認する。
- AWSの無料利用枠（新規アカウント向けクレジット等）を適用できる場合がある。
- 想定外の課金を防ぐため、構築前に **AWS Budgets** で予算アラート（例：月10ドルを超えたらメール通知）を設定する。

#### 8-7. AWS構成のデメリット・注意点

| 項目 | 内容 |
|---|---|
| 費用 | A案（0円）と比べて、最小構成でも毎月固定費が発生する |
| 学習コスト | VPC・IAM・セキュリティグループなど、理解すべき概念が多い |
| 運用負荷 | 権限設定・ネットワーク設定の誤りがそのまま情報漏えいにつながるため、設定内容の確認を自分で行う必要がある |
| 構成管理 | 管理画面での手作業は再現しにくいため、本格運用時はAWS CDKやTerraformでの構成のコード化を検討する |
