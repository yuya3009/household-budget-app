# 家計簿アプリ 要件定義書

## 第12章 テスト計画書（一次開発）

[画面一覧書](03_画面一覧書.md)・[画面遷移図](04_画面遷移図.md)・[機能一覧書](05_機能一覧書.md)・[テーブル定義書](07_テーブル定義書.md)・[API仕様書](09_API仕様書.md)を基に、一次開発のテスト方針と確認観点を定義する。
開発者1名（テストも開発者自身が行う）の個人開発を前提とし、**自動で何度でも回せること** と **続けられる量に絞ること** を重視する。

---

### 1. テスト方針

#### 1-1. テストレベル

| レベル | 単位 | 目的 | 主な確認内容 |
|---|---|---|---|
| UT（単体テスト） | 1画面／1API／1ロジック | 部品が正しく動くことを確認する | バリデーションの網羅、表示内容、DB登録内容 |
| IT（結合テスト） | 複数画面にまたがるシナリオ | ユーザ操作が最後まで通ることを確認する | 画面遷移、戻る操作、他画面への反映、DBの最終状態 |

#### 1-2. 役割分担の考え方

- **網羅はUTで行う**。入力パターン（必須・桁数・境界値・形式）はUTで全件確認する。
- **ITは流れを確認する**。バリデーションはITでは代表ケース（エラー表示 → 修正 → 登録成功）のみとし、UTと重複させない。
- 画面から送れない値（範囲外の数値、種別違いのカテゴリIDなど）は、画面ではなく**APIを直接呼び出して**確認する。
- グラフは画像比較を行わず、**APIのレスポンス値とDBの集計値の一致**で確認する。画面側は表示有無・ラベル程度に留める。

| 観点 | UT | IT |
|---|---|---|
| バリデーション | ◎ 全パターン | △ 代表のみ |
| DB登録 | ◎ 1操作ごとの値 | ○ 一連の操作後の最終状態 |
| 画面遷移・戻る | × | ◎ |
| 他画面への反映 | × | ◎ |

### 2. 使用ツール

| 用途 | ツール | 役割 |
|---|---|---|
| 画面テスト（UT・IT） | **Playwright**（`@playwright/test`） | ブラウザ操作による画面テスト。テストランナーとしても使用する |
| APIテスト | **Playwright**（`request` フィクスチャ / APIRequestContext） | APIを直接呼び出し、画面から送れない値のバリデーションやレスポンスを確認する |
| ロジックテスト | **Playwright**（ブラウザを使わないテスト） | 固定費自動計上（FUC-009）の日付計算など、関数単体のテスト。ツールを増やさないためPlaywrightのテストランナーで実行する |
| DB検証（自動） | **Prisma Client** | テストコードからテスト用DBを直接参照し、登録・更新・削除後のレコードを検証する。テスト前のデータリセット・シード投入にも使用する |
| DB検証（目視） | **Prisma Studio** | テスト失敗時の調査や、手動確認時にDBの中身をブラウザで確認する |
| テスト用DB | Docker（PostgreSQL） | 開発用DBとは別のテスト専用DBを [デプロイ・インフラ方針書](11_デプロイ・インフラ方針書.md) と同じDocker Composeで起動する |

#### 2-1. 選定理由

| ツール | 理由 |
|---|---|
| Playwright | 画面操作・API呼び出し・ロジックテストを1つのツールで実行でき、個人開発で覚えるツールを最小限にできる。ブラウザの「戻る」操作（`page.goBack()`）やスマートフォン表示（デバイスエミュレーション）にも対応しており、ITで確認したい戻る操作をそのまま自動化できる |
| Prisma Client | [技術スタック書](06_技術スタック書.md)でORMとしてPrismaを採用しているため、アプリと同じスキーマ定義・型でDBを検証できる。SQLを手書きせずに済み、スキーマ変更時も型エラーで検知できる |

#### 2-2. テスト実行時の設定

| 項目 | 設定 | 理由 |
|---|---|---|
| 並列実行 | `workers: 1`（直列実行） | テスト間でDBを共有するため、並列実行するとデータが干渉する |
| DBリセット | 各テストの前にテーブルをTRUNCATEし、シードデータ（ユーザ1件・デフォルトカテゴリ）を投入 | テストの実行順序に結果が左右されないようにする |
| 表示サイズ | スマートフォン（例: iPhone 15）のデバイス設定 | ボトムシート・フッターなどスマートフォン前提の画面のため |
| 日付の固定 | ブラウザ側は `page.clock` で固定。サーバ側は環境変数等で「現在日時」を注入できるようにしておく | 「今日」「未来日」「当月」を扱うテストを、実行日に関係なく同じ結果にする |
| 要素の指定 | `getByRole` / `getByLabel` を優先し、難しい箇所のみ `data-testid` を付与 | 画面のデザイン変更でテストが壊れにくくする |
| 失敗時の記録 | スクリーンショット・トレースを失敗時のみ保存 | 全件保存すると容量と確認の手間が増えるため |

#### 2-3. ディレクトリ構成（案）

```
tests/
├── fixtures/        # DBリセット・シード投入・Prisma Clientのフィクスチャ
├── ut/
│   ├── screens/     # 画面単位のテスト（scr002.spec.ts など）
│   ├── api/         # APIテスト
│   └── logic/       # 固定費自動計上などのロジックテスト
└── it/
    ├── scenarios/   # 業務シナリオ
    └── navigation/  # 画面遷移・戻る操作
```

### 5. 実施タイミングと完了基準

| 項目 | 内容 |
|---|---|
| UT | 実装・修正のたびに該当画面のテストを実行する。push前に全UTを実行する |
